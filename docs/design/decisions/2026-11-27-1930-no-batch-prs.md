## Why this record exists

#3370 gathered 21 sub-PRs, direct commits and repeated `main` syncs on one session branch, then tried to land them as one integration PR into `main`. It took most of a day: 767 files and 228 commits had to be reviewed again as a whole, the review found problems the sub-PRs had never been checked against (release signing, billing, migrations), merges of `main` kept conflicting, and every fix restarted a full CI run that the whole batch had to pass at once. Each sub-PR was already green on its own; batching them added the cost and none of the safety.

## Decision

1. **Every PR targets `main`.** A feature branch is cut from `main` and merges into `main`. No session, epic or integration branch collects other PRs.
2. **No batch PRs.** One PR is one independently verifiable change. Do not combine finished PRs into a new one, and do not merge PRs into another PR's branch.
3. **Changes that depend on each other land in order,** each green on `main` by itself: expand–contract for wide refactors, a feature flag or an unused-until-wired path for a feature that spans several PRs, and stacked PRs that are retargeted to `main` as each base merges (§ 5 rule 4).
4. **Paired public/hosted changes** keep their existing order (public PR, then the hosted PR, then the overlay pin). That is one PR per repository, not a batch.
5. The exceptions for approved epic batches are withdrawn. Work still on such a branch lands as separate PRs to `main`.

## Consequences

- `docs/dev-workflow.md` § 5 and `AGENTS.md` say "no batch or integration PRs"; the `implement-spec` and `to-tickets` skills merge each ticket to `main` instead of to an integration branch.
- A reviewer closes a PR that bundles other PRs and asks for them to land separately.
