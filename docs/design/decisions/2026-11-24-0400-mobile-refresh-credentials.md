# iOS: refresh credentials keep the app signed in

- Date: 2026-11-24
- Source: Alex, 2026-11-24, tired of the iOS app signing people out: 「你按照 best practice 继续往下做就行了…该合并合并…都不需要再问我了」, relayed by the coordinator with its agreed plan (a rotating mobile refresh token beside the session cookie). Builds on #3209 (keep renewed sessions, confirm a 401 before signing out).
- Rule: —
- Code: `lib/auth-mobile-refresh.ts`, `drizzle/20261124035101_mobile_refresh_tokens.sql`, `apps/mobile/lib/access-keeper.ts`, `apps/mobile/lib/refresh.ts`.

- The session cookie stays the iOS app's access credential. A signed-in phone trades it once for a refresh token (`POST /api/auth/mobile-refresh/exchange`, native app only: a browser's own Origin is refused). Existing installs move over on their next launch after the API deploy and the OTA, without signing in again.
- `rotate` trades a refresh token for a one-hour access session, set as the session cookie like a sign-in, and the next refresh token. Refresh tokens are `mkmr_` + 32 random bytes, stored only as sha256, single use, valid 60 days from their rotation and never past the family's 180-day end; then the person signs in again. A refresh token is never an access credential (`lib/api-auth.ts`, `desktopBearerHeaders`).
- Settled here: **the access session is renewed in place**, a new token and a one-hour expiry on the same session row, rather than a new session each hour. The app's outbox, push registrations, review sessions, live channel and the session's 2FA and SSO fields are bound to the session id; a new id every hour would clear unsent messages and re-register pushes. The previous cookie still stops working at the rotation. Only when Better Auth already deleted the row (its own stale cookie arrived after the hour) is a new session minted through Better Auth's internal adapter; it takes the family's copy of the sign-in's second-factor assurance and the phone's push registrations.
- A rotated session never slides: a `BEFORE UPDATE OF "expiresAt"` trigger on `session` keeps the expiry a rotation gave it, whatever reads it. The first, exchanged session keeps its ordinary lifetime until its first rotation.
- Replay: a used token presented again revokes the family and ends its session (`refreshRejected`), except within 60 seconds of its use while the token it produced is still unused; that is a lost answer, and it rotates again from there and supersedes the lost child. The app retries a failed rotation once at once to land inside that window.
- Revocation: deleting a live access session (sign-out, 登录设备, 退出其他所有设备, a password reset, enterprise deprovisioning, any SQL delete) revokes the family it backs (`AFTER DELETE` trigger). An expired one: Better Auth deleting it because its own stale cookie arrived is not a sign-out; any other request deleting it is, and so is 退出其他所有设备, which Better Auth runs only over unexpired sessions. 登录设备 lists a phone kept signed in by its family and revokes it. Signing out on the phone also calls `revoke`. Deleting the person deletes their tokens. A revoked session can still read through the 5-minute cookie cache (`SESSION_COOKIE_CACHE_SECONDS`) as today; a revoked refresh token stops at once.
- A phone is still signed in for its pushes while its family backs its session (`PHONE_SESSION_SIGNED_IN` in `lib/mobile-push.ts`), so a phone in a pocket keeps its notifications after the hour.
- Organization SSO sessions keep today's session: `exchange` answers 409 `refreshUnavailable`, because SAML lineage and deprovisioning belong to the identity provider's own session. Supporting them is a follow-up.
- The app: per account in the keychain (`accountStorageKey(id, 'refresh')`) with the user it belongs to; it exchanges once per session per launch or foreground, renews when the app comes to the front or before a request when the access session ends within 5 minutes, and on a 401 shares one rotation among all requests and replays each once. Only `refreshRejected` (or no credential), confirmed by #3209's session check, signs out; a network error, timeout, 5xx or 404 never does. With a credential held, the sign-in gate keeps showing the saved account while the cookie is renewed, offline included. No timers or polling.
- Known limit: other deferred checks that require the acting human's session to be unexpired (approved writes, Factory approvals, MCP tokens bound to a session) see a phone's session expire an hour after the app was last used, and fail closed. Nothing deferred from the phone was found to need more today; widen those checks with the same predicate if one does.
- Release: additive migration; old app builds and the web are unchanged and `HOSTED_API_FLOOR` is not raised. The migration must be applied in the release owner's database window (#1954) before this API serves, because push delivery and 登录设备 read the new table. Until the API serves, the app's exchange gets 404 and the app keeps #3209's behaviour.
